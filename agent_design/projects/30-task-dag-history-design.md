## 1. 目标与非目标

**要**：一次 Turn 的全部任务（含已结束的）在一张图里完整可见；能回答"为什么这次慢了""哪一步失败了""谁等了谁"。

**不要**：不做跨机器的分布式追踪（那是另一个量级）；不改 harness 的任务模型；不在图里放 token 级明细。

## 2. 现状（证据）

| 事实           | 值                                                                             |
| -------------- | ------------------------------------------------------------------------------ |
| 图数据源       | `tasks` 事件，**只有活着的任务**                                               |
| 结束的任务     | 立刻离开图；`useFinished` 在客户端留 30 个、30 秒后丢弃                        |
| 终止任务可读   | `tasks/ended` 按 **id** 查，需先知道 id                                        |
| 终止任务可枚举 | `tx.scanTasks(query, limit, cursor)`，可按 conversation/kind/status 过滤并排序 |
| 现有布局       | 按 `owner` 深度分列，`NODE_WIDTH 192`、`COLUMN_GAP 44`                         |

关键结论：**历史数据已经在库里，缺的是"按会话扫描 + 呈现"这一层**，不需要新的采集或存储。`scanTasks` 的签名见 `node_modules/@earendil-works/pi-durable/dist/types.d.ts:911`，`TaskQuery` 见 `:761`。

## 3. 核心概念：Run

> **Run = 一次顶层 `pi.generation` 任务，加上它派生出的全部任务。**

- 顶层任务的判据：`kind === 'pi.generation'` 且没有 `owner`。
- 一个会话的每次输入 → 一个 Run。
- Run 内的子任务是它的 `owner` 树；跨会话的 `on` 等待边仍按虚线画。

这样"从开始到结束"就有了自然的边界：**一个 Run 的开始就是它的顶层任务启动，结束就是它和它所有后代都终止**。

## 5. 节点显示什么

**折叠态**（默认，38 px 高）：图标 + 名称 + 状态点 + 时长。

**展开态**（点击）：

- 工具名 + 参数第一行（如 `pnpm test --run`）
- 所属 agent 与模型
- 开始偏移 / 结束偏移 / 时长
- 结果：`done` / `failed` / `aborted`，失败附错误首行
- 重试次数、子任务数
- token 与成本（若记录里没有则留空，不显示 0）

**历史节点的视觉**：已结束的统一降饱和（不透明度 60%），失败用 warning 色；**不再 30 秒消失**。

## 6. 两种视图

### 6.1 Structure（结构视图，默认）

沿用现有按 `owner` 深度分列，但：

- 画完整的历史树，不再只画活着的
- 已完成的子树默认折叠成 `+N` 芯片，点击展开（几十个节点的图必须能折）
- 跨任务 `on` 等待仍画虚线

适合回答：**谁属于谁、谁等了谁**。

### 6.2 Timeline（时间视图，新增）

- **横轴 = 时间**（从 Run 开始算起）
- **纵轴 = 泳道**，每个会话/agent 一条
- 每个任务是一根横条，从开始到结束
- 等待边画成从"等待者开始"到"被等待者结束"的连线

适合回答：**为什么慢、哪里有空转、哪一段时间在并行**。

```
┌─ time ─────────────────────────────────────────────────────────┐
│        0s      60s     120s    180s    240s    300s            │
│ @ultimate #71600  ████████████████████████████████████████     │
│ @scout #31            ██████                                   │
│ @worker #44                    ████████████████                │
│ @reviewer #52                              ██████████          │
└────────────────────────────────────────────────────────────────┘
```

### 6.3 关键路径

两种视图共用一个可选开关：**高亮关键路径**——从 Run 开始到结束、耗时最长的那条依赖链。它通常就是"这次为什么用了 3 分钟"的答案。

## 7. 历史保留与性能

**不新增存储**。数据已经在 durable 任务表里，只是现在没有任何接口按时间读它。

新增一个只读 action：

```ts
tasks/history  { conversationId?, before?, limit? }
  → { runs: [{ id, startedAt, endedAt, outcome, taskCount, ... }], cursor? }
tasks/run      { id }
  → { tasks: TaskRecord[] }   // 一次 Run 的全部任务，含已结束
```

- 用 `tx.scanTasks({ conversationId, kind?, status?, order }, limit, cursor)` 分页。
- 默认每页 20 个 Run；选中某个 Run 才拉它的全部任务（上限 5000 条，超出则截断并提示）。
- 浏览器按 Run 缓存，切换不重复拉。
- **保留策略只是"能不能看到"的问题**：库里不删，界面默认显示最近 50 个 Run，可调。

## 9. 分期

| 期     | 内容                                                              | 价值           | 成本 |
| ------ | ----------------------------------------------------------------- | -------------- | ---- |
| **P1** | `tasks/history` + `tasks/run`，Run 列表，Structure 视图画完整历史 | 立刻得到"全貌" | 中   |
| **P2** | Timeline 视图 + 关键路径                                          | 回答"为什么慢" | 中   |
| **P3** | 过滤、折叠、跳转、成本/token 汇总                                 | 好用           | 小   |

## 10. 成本估算

- 服务端：2 个只读 action + 分页（~150 LOC）
- 前端：Run 列表、摘要、Structure 完整历史、折叠（~600 LOC）
- Timeline + 关键路径（~400 LOC）
- 测试：布局纯函数、分页、Run 分组（~250 LOC）

**P1 约 2 天；P1+P2 约 4 天。**
