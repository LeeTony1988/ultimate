## 1. 目标与非目标

**要**：一次 Turn 的全部任务（含已结束的）在一张图里完整可见；能回答"为什么这次慢了""哪一步失败了""谁等了谁"。

**不要**：不做跨机器的分布式追踪；不改 harness 的任务模型；不在图里放 token 级明细。

## 2. 现状（证据）

| 事实           | 值                                                                             |
| -------------- | ------------------------------------------------------------------------------ |
| 图数据源       | `tasks` 事件，**只有活着的任务**                                               |
| 结束的任务     | 立刻离开图；客户端留 30 个、30 秒后丢弃                                        |
| 终止任务可读   | `tasks/ended` 按 **id** 查，需先知道 id                                        |
| 终止任务可枚举 | `tx.scanTasks(query, limit, cursor)`：按 conversation / kind / status 过滤排序 |
| 现有布局       | 按 `owner` 深度分列，`NODE_WIDTH 192`、`COLUMN_GAP 44`                         |

`scanTasks` 见 pi-durable 1.5.0 的 `types.d.ts:911`，`TaskQuery` 见 `:761`。实现调查发现，一次输入不只对应一个 generation：工具轮结束时 pi-durable 创建新 generation 并转移同一 Run 的控制权（`harness/generation.js:916–923`）。因此需要结合 submission、entry 和 task 重建回合边界，不能把 generation 数当成回合数。

## 3. 核心概念：Run

> **Run = 一个会话中从输入 submission 到回答或终止的一次回合，包含期间所有 generation、工具轮和可关联的子代理工作。**

顶层 `pi.generation` 是回合中的执行节点，不是回合边界。同一回合接收的 steer 可以共享一个 answer；排队的 follow-up 开始下一回合；没有输入 entry 的 continue、失败、`turn_limit` 和 reset 也要分别处理。通过持久 submission、entry 和任务关系重建，无法证明的边界必须标明不确定，不能静默并入另一个回合。

子会话可能由其父会话独立拥有的 background anchor 持有，而不是直接由当前 generation 拥有。能由持久关系证明的关联照实显示；只能根据时间或记录顺序推断的关联必须明确标为推断。终态 task 不保留之前的 `on` 列表，历史等待边以及未保留的重试或嵌套调用成本不能凭空恢复；缺失时显示未知而不是零。

```
│  Legend: ── owns  ┄┄ runs before  ══ critical path                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

**左栏：会话列表**（可多选，默认选中当前会话）

- 每行：`@agent #id` + 该会话的 Run 数 + 最近活动时间
- 勾选的会话决定：① Run 列表里出现哪些 Run；② 图里出现哪些 frame
- 顶部"全选 / 清空"

**中栏上方：Run 列表 / 当前 Run 摘要**

- Run 列表按时间倒序，只列选中会话的 Run
- 选中一个 Run 后，摘要显示任务数、agent 数、工具调用数、token、成本

**中栏主体：图**，每个会话一个 **frame box**：

- 圆角边框 + 左上角标题（`@agent #id`）
- 同一会话的任务全部落在自己的 frame 里
- frame 之间按 Run 内的启动顺序纵向排列
- 只有一个会话时，frame 仍然显示（保持一致，不特殊化）

## 5. 节点显示什么

**折叠态**（默认，38 px）：图标 + 名称 + 状态点 + 时长。

**展开态**（点击）：

- 工具名 + 参数第一行（如 `pnpm test --run`）
- 所属 agent 与模型
- 开始偏移 / 结束偏移 / 时长
- 结果 `done` / `failed` / `aborted`，失败附错误首行
- 重试次数、子任务数
- token 与成本（受 §6 的模式控制）

**历史节点视觉**：已结束降饱和（不透明度 60%），失败用 warning 色，**不再 30 秒消失**。

## 6. 两个 tab

### 6.1 Structure（默认）

- 按 `owner` 深度分列，画**完整历史树**
- 已完成的子树默认折叠成 `+N` 芯片
- 可取得的跨任务 `on` 等待画虚线；终态记录未保留的历史等待不推造
- 可选高亮**关键路径**（从 Run 开始到结束耗时最长的依赖链）

### 6.2 Timeline（独立 tab）

- 横轴 = 时间（从 Run 开始算）
- 纵轴 = 泳道，每个会话/agent 一条，**仍用同样的 frame 分组**
- 每个任务一根横条；可取得的等待边连到被等待者的结束点
- 悬停出详情卡

## 7. 设置

| 设置键              | 默认    | 说明                                            |
| ------------------- | ------- | ----------------------------------------------- |
| `tasks.historyDays` | `3`     | 保留天数；界面只显示这个窗口内的 Run            |
| `tasks.costDetail`  | `'run'` | `run` = Run 级合计；`tool` = 精确到每次工具调用 |

- 放在项目设置里（`.ultimate/settings.json`），图上方的 ⚙ 直接可改。
- 数据本身不删——`historyDays` 只控制**可见范围**，避免误删。

## 8. 接口

```ts
tasks/conversations {} → 会话列表（id、agent、run 数、最近活动）
tasks/history       { conversationIds, before?, limit? } → { runs, cursor? }
tasks/run           { id } → { tasks: TaskRecord[] }   // 一次 Run 的全部任务
```

- 默认每页 20 个 Run；选中才拉全部任务（上限 5000 条，超出截断并提示）
- 浏览器按 Run 缓存

## 9. 交互

| 操作     | 行为                                     |
| -------- | ---------------------------------------- |
| 勾选会话 | 过滤 Run 列表；图里的 frame 跟着变       |
| 点 Run   | 载入并画出该 Run                         |
| 点节点   | 展开详情卡                               |
| 双击节点 | 跳到对应会话/工具调用                    |
| 折叠子树 | 点 `+N` 芯片                             |
| 过滤     | 全部 / 只看失败 / 只看 >10s              |
| ⌘K       | "Show the task DAG" / "Show run history" |
