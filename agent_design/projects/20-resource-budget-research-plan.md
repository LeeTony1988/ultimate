## 1. 先量化问题（否则没有验收线）

现状事实：

| 事实             | 值                     | 证据                           |
| ---------------- | ---------------------- | ------------------------------ |
| 本机逻辑核       | 16                     | `Win32_ComputerSystem`         |
| unit 测试 worker | 8                      | `vite.config.ts:223`           |
| e2e 测试 worker  | 4                      | `test/e2e/vitest.config.ts:10` |
| project 进程     | 每个 project 一个 host | `server/main.ts:68`            |
| 跨进程预算       | **无**                 | 全仓无 budget/semaphore        |

推论：N 个 project 各跑一次 unit，峰值就是 `N × 8` 个 worker 进程。

今天已发生的事（可作为对照）：

- 并行分支跑门禁时 load 到 **31.93**，同一批测试出现 9 个文件 / 65 个测试红；宿主机空闲时同批全绿。
- 多次出现 `Test timed out in 30000ms`，隔离重跑即过。

**要采的数据**（调研第一件事）：

1. 在 1 / 2 / 3 个并发 project 下各跑 3 次 unit 与 e2e，记录：墙钟时间、峰值 worker 数、`/proc/loadavg`（或 Windows 的处理器队列长度）、红率。
2. 单 project 独占时的墙钟时间作为基线。
3. 找出"红率开始上升"的峰值 worker 阈值——这决定预算该定多少，而不是拍脑袋定 8。

## 2. Q1：worker 能不能跨进程共享

**先核实 vitest 的 worker 生命周期**（读 `node_modules/vitest` 的 pool 实现与文档，不靠记忆）：

- 默认 pool 是什么（forks / threads / vmForks），worker 由谁 fork。
- worker 是否绑定启动它的进程；一个 worker 能否服务第二个 vitest run。
- `--maxWorkers` 的生效点（每个 run 自己的池，还是全局）。

基于此评估三条路，逐项打分（可行性 / 隔离性 / 失败面 / 改动量 / 可观测性）：

### A. 租约式预算（semaphore）

每个 run 先向协调者申请 N 个 slot，拿到后以 `--maxWorkers N` 启动，退出时归还。

- **不是共享 worker**，是共享"额度"：`Σ maxWorkers ≤ 预算`。
- 每个 run 仍用自己的进程池，隔离性不变。
- 已确认可行：`vp test --maxWorkers <n>` 接受数字或百分比。
- 主要成本：所有发起方（lander 的 check、agent 的 `powershell` 里的 `pnpm test`、dream）都必须走同一个入口，否则预算形同虚设——**这是最大的风险点，要专门设计"怎么保证没人绕过"**。

### B. 中央执行器

一个进程代所有 project 跑测试，worker 池真正只有一份。

- 字面满足"全局池"。
- 代价：结果归属（哪个 project、哪个会话、哪次 check）、cwd 与 checkout 隔离、输出流式回传、单点故障、升级时正在跑的测试全部中断。
- 要验证：一个进程内能否并发起多个 `startVitest()` 且互不干扰（读 vitest 的 programmatic API）。

### C. OS 级限制

用 Windows Job Object（`lib/windows-process-group.ts` 已有）或 POSIX cgroup/nice 限制整个 project 进程树的 CPU 份额。

- 不解决 worker 数量，只解决"抢 CPU"。
- 优点：对绕过预算的跑法也有效。
- 缺点：不能给 lander 优先权；通常需要管理员权限（cgroup v2 需要）。

**预期结论（待证实）**：Q1 的答案大概率是"不能字面共享，但等价目标可达成"。调研要把这一点坐实或推翻，而不是假设。

## 3. Q2：预算管什么

只做 CPU worker 是不够的——今天咬人的还有别的。调研要把每一类资源的持有者和释放条件写清楚：

| 资源      | 单位       | 谁持有                         | 释放条件                    |
| --------- | ---------- | ------------------------------ | --------------------------- |
| CPU slots | worker 数  | 测试/构建 run                  | 进程退出                    |
| 重进程    | 实例数     | preview host、lander、子代理   | 进程退出或 stop             |
| 临时磁盘  | MB         | worktree、preview home、bundle | 清理（注意 `EBUSY` 的教训） |
| 模型并发  | 在飞请求数 | 每个 host 的模型调用           | 响应返回                    |

同时明确**优先级**：landing gate > 前台 agent 的检查 > 后台 dream/自动化。要设计抢不到额度时是排队还是降级（例如 dream 直接让路）。

## 4. Q3：租约与回收

这是整个模块最容易出错的地方，今天已经踩过一次同类问题（`cleanPreview` 先 `rm` 后关数据库 → `EBUSY`）。

要设计的部分：

- **令牌**：`{id, owner(project+conversation), slots, pid, startedAt, expiresAt, heartbeat}`。
- **租约而非锁**：持有者必须心跳；没有心跳就过期，不需要人工介入。
- **崩溃回收**：进程死了但没归还 → 靠 pid 存活 + TTL 双条件回收。单靠 pid 在 pid 复用时误判，单靠 TTL 会误杀长任务，两者要组合。
- **幂等归还**：重复归还、归还已过期的令牌都不能报错。
- **时钟**：用单调时间算 TTL，不依赖墙钟。
- **可观测**：`resources` 面板/命令要能回答"现在谁占了什么、排队的谁先"。

## 5. 实验与验收

| 指标                  | 现状基线     | 验收线                            |
| --------------------- | ------------ | --------------------------------- |
| 峰值并发 worker       | 无上限       | ≤ 预算                            |
| 单 project 独占墙钟   | 待测         | 退化 ≤ 15%                        |
| 3 个 project 并发墙钟 | 待测         | 明显优于无预算（否则预算无意义）  |
| 红率（同一批测试）    | 高负载下升高 | 有预算时与独占时持平              |
| 崩溃后恢复            | —            | 30 秒内额度自动回到池中，无需重启 |

实验矩阵：`1/2/3 并发 × 有/无预算 × 3 次`，全部记录原始数据。
