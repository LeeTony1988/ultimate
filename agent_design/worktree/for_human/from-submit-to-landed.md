# 从 submit 到 landed

子 agent 改完代码，代码怎么回到主分支？Ultimate 有两条路，选错会带来完全不同的风险。

## 一、两条路径

|          | `workspace land`（同步）   | `workspace submit`（异步） |
| -------- | -------------------------- | -------------------------- |
| 谁触发   | agent 直接调用             | agent 提交，进队列         |
| 合并方式 | `git merge --ff-only`      | lander 合并后 ff           |
| 跑检查   | 不跑                       | 跑全套                     |
| 推送     | 不推                       | 推送（按配置）             |
| 失败处理 | 直接拒绝，agent 自己处理   | diagnose / fix，最多一次   |
| 适用     | 小改动、agent 自己就能确认 | 需要门禁和审查的交付       |

一句话：**land 是快进，submit 是交付。**

## 二、submit 的门槛

提交前必须满足：

- 是顶层 main 上的提交（分支提交要先回主分支）；
- 带一段非空的 `divergence`——结果与原始任务相比，哪里不一样（新约定、换了做法、范围变了；完全一致就写"无"）；
- checkout 干净；
- 分支在提交后没有被移动。

`divergence` 不是形式主义。它是给下一个人（和未来的自己）看的最重要的一句话：**这次交付和当初说的哪里不同。**

## 三、排队

每个源（项目主 checkout）只有一条 FIFO 队列：

```
queue: [A(tip 1a2b) → B(tip 3c4d) → C(tip 5e6f)]
```

规则：

- 同一 tip 重复提交会去重；
- 提交立即返回队列位置和负责落地的 `@lander` 会话；
- 每个源同时只有一个 live lander task，避免两个任务同时 merge。

"每源一条队列"看起来保守，但它消灭了最麻烦的一类 bug：两个提交同时快进同一个分支，第二个失败后重试，重试又撞上第三个。

## 四、lander 的一次循环

```
拿队首
  │
  ├─ 在自己的 detached 集成 checkout 里 reset 到目标 tip
  ├─ fetch 远端；如果远端领先，先合并远端
  ├─ 合并这次提交
  ├─ 跑项目 setup
  ├─ 按顺序跑检查（数组元素是一组并发）
  ├─ 复核：HEAD 没变、工作区没变
  ├─ fast-forward 目标分支
  ├─ 记录 landed（先于 push）
  ├─ push（非强制，失败重试一次）
  └─ 回报提交者
```

几个设计点：

- **lander 有自己的 checkout**，永远 detached，不在用户的分支上工作。这样集成中间态不会污染任何人的工作区。
- **先记录、再推送。** 如果 push 失败，本地 landing 已经生效，报告里写清"已落地、推送失败"，而不是回滚。
- **检查绑定确切 commit。** 检查跑在集成后的 SHA 上；跑完再验一次 HEAD 和工作区，变了就重来。
- **lander 看不到日志正文。** 日志是给人看的，模型只看结构化结果，避免 token 被日志淹没。

## 五、检查怎么跑

- 检查是一个有序数组；数组里的一个元素如果是并发组，组内并行、组间串行；
- 每条检查 2 分钟无输出、10 分钟总时限（项目可配置，配置会同时压缩这两个上限）；
- 失败重跑一次：第二次通过记 `flaky`，第二次失败才算失败；
- 超时记为 `failed`，事件里标 `timeout`；
- 超时由 watchdog 杀掉整个进程组（Windows 用 Job Object）。

flaky 只重跑一次，是刻意的：无限重跑会把"不稳定"伪装成"通过"。

## 六、失败之后

| 配置                  | 行为                                                             |
| --------------------- | ---------------------------------------------------------------- |
| `onFailure: diagnose` | 只解释失败原因，不改代码                                         |
| `onFailure: fix`      | 必须留下一个干净、基于失败 merge 的 commit；随后**所有**检查重跑 |

每次提交最多修复一次。第二次仍失败，不再给模型机会，交给人。

这条规则的价值在于：它承认模型有能力修简单问题，也承认模型会在复杂问题上越修越乱。一次机会，是两者的折中。

## 七、回报与部署

落地后，提交者会收到一张卡片：合了哪些 commit、改了哪些路径、多少行、要不要重启、推送是否成功。

如果项目配置了部署路径前缀，lander 会通过 `workspaces.handoff` 把部署交给对应的 agent，**恰好一次**。部署不阻塞落地：lander 不等部署结果，也不把"部署失败"写进落地状态。

## 八、崩溃之后

lander 的每一步都有 memo 和持久记录。崩溃恢复时：

- 已经记录 `landed` 的提交，新的 lander 任务不再 merge、不再检查，只补 push 和回报；
- 已经 push 成功但没回报的，补回报；
- 没走到 `landed` 的，从头再来。

这就是"先记录 landed、再 push"的原因：它让恢复只需要判断一件事——有没有落地。

## 九、为什么不用 PR

PR 模型假设有远端托管平台、有评审人、有合并队列。Ultimate 的场景是本地优先、单机、agent 自己交付：

- 落地单位是本地分支的一次 fast-forward，不是远端 PR；
- 评审是 review team 在落地前做的，不依赖平台；
- 推送是落地后的动作，失败不影响本地结果。

这不是说 PR 不好，而是说：把 PR 硬塞进本地 agent 工作流，会多出平台依赖和一堆"等 review"的空转。

## 十、常见误解

**"submit 就是 push。"**
不是。submit 是排队交付；push 是落地之后的最后一步，可能失败，且不回滚落地。

**"检查失败可以一直重跑。"**
只重跑一次。第二次失败就停。

**"lander 会在我的分支上操作。"**
不会。它在自己的 detached checkout 里集成，成功后只移动目标分支的指针。

**"失败了模型可以反复修。"**
每次提交只有一次修复机会。
