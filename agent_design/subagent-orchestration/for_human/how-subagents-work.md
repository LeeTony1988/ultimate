# 一次委派是怎么完成的

假设你在一个分支里对 coordinator 说："给登录页补上错误提示，改完告诉我。"

下面是这句话在 Ultimate 内部走过的路。

## 一、先有定义，才有 agent

子 agent 不是一个临时拼出来的 prompt，而是由一份 Markdown 定义描述的：

```markdown
---
name: worker
model: <可省略：省略时跟随父模型>
tools: ...
isolate: worktree
---

（指令正文）
```

定义从三个地方发现，后者覆盖前者：内置 → 用户目录 → 项目目录。同名定义会覆盖；项目还可以用 overlay **追加**指令，但不能删除或改写基础指令。

两条硬规则：

- 定义里列出的工具必须是父 agent 工具的子集。子 agent 不能拥有父没有的能力。
- 默认不把 `subagent` 工具和扩展继承给子 agent，避免无限递归委派。

## 二、start：创建会话，而不是调用函数

`start` 做四件事：

1. 创建子会话（child id 就是会话 id，不是另一套编号）；
2. 创建一个 background anchor 任务，让子会话归它所有；
3. 创建一个 reporter 任务，负责答案回传；
4. 如果 `isolate: worktree`，为它准备一个独立 checkout。

调用者可以选择等待风格：

- **前台**：`start` 一直等到有答案。这只是"等待风格"，不是所有权。
- **后台**：`start` 立刻返回 id，答案之后以输入的形式回到父会话，或者唤醒父会话。

关键区别：**父的当前 run 结束，不代表子 agent 结束。** 子 agent 归 anchor 所有；父被停止时，子 agent 仍然可以继续跑完。

## 三、答案为什么不会丢，也不会重

这是整套机制里最难的部分。答案回传经过一条很窄的通道：

```
子 agent 产生答案
   │
   ├─ 生成一条 answer entry（有稳定 id）
   │
   ▼
reporter 任务 ──► 以 requestId 提交到父会话的 inbox
   │
   ▼
父会话下一次输入前，看到这条答案
```

三个约束让它跨崩溃也成立：

- **每个 start/message 恰好一个 reporter。** 不会两个 reporter 抢着报同一条答案。
- **按 answer entry id 去重。** 同一个答案被扫到两次，只会投递一次。
- **每次投递带稳定 requestId。** 重启后重放，不会产生第二条输入。

还有一个容易漏的细节：如果工具调用本身已经把答案返回给父了（同步场景），队列里的 reporter 必须被标记为"已投递"，否则工具结果和异步报告会变成两份。

系统在重启后会做一次恢复扫描：找出所有还没投递的答案，补投。补投同样按 id 去重。

## 四、wait、steer、follow-up：三种"打断"

| 动作                    | 含义                                               | 常见误解                       |
| ----------------------- | -------------------------------------------------- | ------------------------------ |
| `wait`                  | 等答案，但可以被 steering 打断，返回状态而不是答案 | 以为取消 wait 就是取消子 agent |
| `message`（默认 steer） | 在子 agent 当前工具轮结束时插入新指令              | 以为会打断正在执行的工具       |
| `message {steer:false}` | 排成 follow-up，等当前 run 结束后再执行            | 以为和 steer 一样即时          |

`wait` 返回"还在跑""需要你决定""已完成"这类状态，而不是硬等一个答案。这样父 agent 可以在等待期间处理别的事，也可以被用户的新消息打断。

## 五、stop、land、discard：三种"结束"

| 动作      | 会做什么                                                           | 不会做什么                   |
| --------- | ------------------------------------------------------------------ | ---------------------------- |
| `stop`    | 取消当前 work、待处理输入和 reporter；列出 worktree 里未提交的文件 | 不删除代码，不删除分支       |
| `land`    | 把子 worktree 的分支快进到目标分支                                 | 不 rebase、不 force、不 push |
| `discard` | 删除空闲的 checkout                                                | 不删除分支                   |

`stop` 的实现有一个细节值得学：它先给当前的 run、输入、reporter、watchdog 拍一张快照，再逐个取消。这样重放时不会误杀之后新建的 run。

`land` 的前置条件也很克制：子 worktree 干净、源 checkout 在目标分支、子 agent 没有 live run 和排队输入。源 checkout 里**与本次改动无关**的脏文件不阻塞——因为 `merge --ff-only` 只在真正重叠时才拒绝。

## 六、四种"看起来像子 agent"的东西

| 东西               | 是什么                              | 和子 agent 的区别                           |
| ------------------ | ----------------------------------- | ------------------------------------------- |
| **branch**         | 顶层的特性会话，没有父              | 不归任何会话所有，不是 child                |
| **standing agent** | 常驻 agent，每个项目一个会话        | ownerless、不 fork，例如 @ultimate、@lander |
| **automation run** | 定时/条件触发的运行                 | 复用定义和创建流程，但忽略隔离设置          |
| **review team**    | 多个 reviewer 并行 + 一个 lead 合并 | 是子 agent 的一种编排模式，不是新物种       |

把它们混为一谈，会导致两类 bug：把 branch 当 child 去 stop，或者给 standing agent 算一个不存在的父。

## 七、出错时的行为

| 情况                       | 行为                                                |
| -------------------------- | --------------------------------------------------- |
| provider 报错              | 交给 watchdog：重试一次，仍失败则出失败卡或标记放弃 |
| 子 agent 结束但没有答案    | 必须给出明确的失败文本，不能静默                    |
| 父会话被停止               | 子 agent 继续；答案之后进入父的 inbox               |
| 系统重启                   | reporter 恢复扫描，未投递的答案补投，已投递的不再投 |
| 子 agent 试图 message 用户 | 拒绝；只有 @ultimate 能直接对用户说话               |

## 八、常见误解

**"子 agent 就是另一个模型调用。"**
不是。它有独立会话、独立工作目录、独立生命周期，还能在父停止后继续工作。

**"foreground 意味着父拥有子。"**
不是。foreground 只是调用者选择等答案；所有权在 anchor 上。

**"reporter 是个回调，失败重试就行。"**
回调重试会产生重复答案。reporter 的正确性靠 requestId + answer id + receipt，而不是靠重试次数。

**"工具限制能当沙箱。"**
不能。工具限制只是"模型看不到某些工具"，不是安全边界；真正的隔离是工作目录隔离，而且也不是安全边界。
