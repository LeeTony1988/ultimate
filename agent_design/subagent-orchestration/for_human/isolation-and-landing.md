# 隔离与合并：子 agent 的代码放在哪

多个 agent 同时改一个仓库，最先出问题的不是模型，而是文件系统：两个 worker 同时改同一个文件，谁也不知道对方的改动；一次 `git checkout` 会把别人的半成品冲掉。

Ultimate 的解决办法是给每个需要写代码的会话一个独立的 Git checkout（worktree）。这篇文章讲清楚它怎么创建、怎么保护、怎么合并回来。

## 一、一个会话一个 checkout

命名是公式，不是随机：

```
路径：<home>/worktrees/<conversationId>
分支：ultimate/<home-hash6>-<conversationId>
起点：创建时父 checkout 的 HEAD
```

公式化的好处是**可重建**：进程重启、记录丢失、checkout 被回收之后，系统都能按同一个路径和分支名把它找回来。如果路径是随机生成的，一次崩溃就可能留下一堆没人认领的目录。

创建不是同步完成的：

1. 创建事务只写一条 `preparing` 记录；
2. 一个持久后台任务执行 `git worktree add`；
3. 在 checkout 里跑项目配置的 setup 命令；
4. 全部成功，才把状态改成 `ready`。

setup 命令从项目设置里读，在 checkout 内、通过宿主 shell、带 `ULTIMATE_SOURCE` 环境变量执行，默认 2 分钟超时。失败时保留输出尾部——下一次工具调用会原地重试，而不是让 agent 面对一个永远坏的目录。

## 二、门禁：Git 是真相

"记录说 ready"不算数。每次工具调用前，系统都会验证三件事：

- 记录状态是 `ready`；
- checkout 真的在磁盘上；
- `git worktree list` 里真的登记了它。

任何一条不成立，工具调用被 block，并返回原因。这个设计解决了一个很实际的问题：记录和磁盘会不同步——用户手动删了目录、Git 自己清理了元数据、磁盘换了挂载点。**以 Git 为准，记录只是缓存。**

## 三、它隔离了什么，没隔离什么

隔离的是**工作目录**：agent 的工具 cwd 指向自己的 checkout，`git status`、构建、测试都只看到自己这一份。

没有隔离的是**整个文件系统**：用绝对路径仍然能访问别的 checkout。所以：

- 它是并发安全的机制，不是安全边界；
- 不要把"只读 agent"当成"碰不到别的东西"；
- 真正的权限控制要靠工具限制和审核流程，不能靠 worktree。

## 四、land：只快进，不重写历史

子 agent 干完活，代码要回到目标分支。同步路径叫 `land`，规则只有一条：**只允许 fast-forward**。

前置检查：

| 检查                                 | 原因                       |
| ------------------------------------ | -------------------------- |
| 子 worktree 干净                     | 未提交的改动不该被悄悄带走 |
| 源 checkout 在目标分支               | 否则 ff 的目标不明确       |
| 子 agent 没有 live run、没有排队输入 | 避免边写边合               |
| 分支没有在创建后被移动               | 防止合错版本               |

注意一个容易误解的点：源 checkout 里**与本次改动无关**的脏文件不阻塞。`merge --ff-only` 只在两边真正改到同一个文件时才拒绝。要求"整个仓库绝对干净"会把大量正常工作卡死。

land 的结果会告诉提交者：合了哪些 commit、改了哪些路径、多少行、要不要重启。**它不会 push**——同步 land 只动本地。

## 五、submit：需要检查与推送时走这条路

如果改动要跑全量检查、要推送远端，就不该用同步 land，而应该 `workspace submit`：

- 提交进入该源的 FIFO 队列；
- 每个源只有一个 `@lander` 常驻会话在处理；
- lander 在独立的集成 checkout 上合并、跑 setup、跑检查、确认树没变、fast-forward 目标分支、记录落地、再 push；
- 失败按 `diagnose` / `fix` 处理，每次提交最多给模型一次修复机会。

这条链路的细节在 `../../worktree/for_human/from-submit-to-landed.md`。这里只需要记住分工：**land 是 agent 自己能做的快进；submit 是需要门禁的交付。**

## 六、discard 与回收

`discard` 删除 checkout，但**保留分支**。这个区分很重要：checkout 是工作空间，分支是工作成果。删错了目录，提交还在；删错了分支，工作就没了。

回收（release）更保守，只有同时满足这些条件才删：

- checkout 干净；
- 分支已落地；
- 没有未回收的子代；
- 会话空闲、没有排队输入。

只要有一条不满足，就保留并报告原因。移除的 checkout 下次被请求时会按原路径重建：未落地的分支原样 checkout，新起点取它的 tip；已合并或已删除的分支从目标分支重新开始。

## 七、冲突与失败

- **合并冲突**：不自动解决，交给 lander 模型或提交者；同步 land 直接拒绝。
- **setup 失败**：保留输出尾部，下一次工具调用重试。
- **检查失败**：只重跑一次；第二次通过记为 flaky，第二次失败才失败。
- **推送失败**：本地落地已经记录，不回滚；报告里写明推送状态。
- **嵌套隔离**：先准备祖先 checkout，再建子 checkout。

## 八、常见误解

**"worktree 是沙箱。"**
不是。它只改工作目录，绝对路径照样能出去。

**"land 等于发布。"**
不是。land 只做本地快进，不 push；push 是 lander 的事。

**"discard 会删分支。"**
不会。discard 删 checkout，分支保留。

**"记录说 ready 就能用。"**
不能。必须磁盘存在且 Git 登记，否则工具会被 block。
