# Ultimate 是怎么"改自己"的

一句话：Ultimate 的自进化不是"模型随手改自己"，而是一条**有持久状态、有闸门、可回滚、可验证**的回路。理解了这条回路，就理解了它为什么敢在运行时修改自己，又为什么很少真正改坏。

## 一、回路长什么样

```
        你说话 / 它干活
             │
             ▼
  观察  trace、会话历史、tally、失败与纠正
             │
             ▼
  反思  Dream 六个 pass、记忆审查
             │
             ▼
  决策  你逐条批准；hands-off goal 时它代决并记录理由
             │
             ▼
  编码  记忆 / 技能 / agent 定义 / 扩展 / 核心代码 / 上游
             │
             ▼
  验证  预览、测试、review、lander
             │
             ▼
  生效  热重载、核心换代（restart）、上游更新
             │
             ▼
  记录  记忆、落地说明、proposal 状态
             │
             └──────► 回到观察
```

这条回路里最有价值的不是某个工具，而是**分层**：改一条记忆和改一行核心代码，风险差了三个数量级，不能用同一套流程。

## 二、六层修改面

| 层                 | 改什么                                  | 谁能改                     | 怎么生效                            | 怎么回滚                        | 代价     |
| ------------------ | --------------------------------------- | -------------------------- | ----------------------------------- | ------------------------------- | -------- |
| **L1 记忆**        | 决策、事实、教训                        | @ultimate（你可删除）      | 立即；下一个分支的 brief 里出现     | 再写一批相反的操作；或你 forget | 几乎为零 |
| **L2 指令**        | `agents/*.md`、技能、`AGENTS.md`        | 你，或 @ultimate（配置类） | 下一次请求 / 下一次子 agent 启动    | 改回文件                        | 低       |
| **L3 配置**        | settings、扩展开关、trust、模型         | 你，或 @ultimate           | 热重载（部分要重启）                | 改回 JSON                       | 低       |
| **L4 扩展 / 表面** | `extensions/<name>` 的 server/web facet | 只能走分支                 | server facet 重载；web facet 热更新 | 删除目录 / 回滚提交             | 中       |
| **L5 核心**        | `server/`、`shared/`、`web/`            | 只能走分支 + lander        | 重启（core swap）                   | 回滚提交 + 重启                 | 高       |
| **L6 上游**        | clone 的 `origin`                       | 你，或 agent 调 `update`   | fast-forward + install + restart    | 不自动回滚，靠执行前拒绝        | 高       |

分层原则只有一句：**能用 L1 解决的不要用 L2，能用 L2 解决的不要用 L4，能用扩展解决的不要改 L5。**

原因不是"代码更贵"，而是每上升一层，验证面、回滚成本和用户可见风险都指数上升。产品规则因此写成："配置自己写，会运行的代码交给 coordinator 分支。"

一个具体的例子：

- 你说"以后提交前先跑 `pnpm check`"——这是 L1，一条记忆就够了；
- 你说"所有 worker 都不许改测试"——这是 L2，改 agent 定义；
- 你要一个全新面板——这是 L4，新建扩展目录，走分支；
- 你说"重启时别丢正在跑的对话"——这是 L5，改核心，走分支 + lander + restart。

## 三、为什么系统提示里没有构建号

热重载和重启会改变 build id。如果 build id 写进 system prompt，每次重载都会让整个 prompt cache 失效，成本和延迟一起爆炸。

Ultimate 的做法是把"我换了哪份代码"变成一条**输入**，而不是系统提示的一部分：

- system prompt 跨构建保持字节稳定；
- 每次请求前，把当前 build id、clone HEAD、指令与文档哈希，和这个会话上次看到的比较；
- 如果有变化，就在用户输入之前插入一条说明："Build changed: a → b · generation N · changed: …"。

模型因此先看到"我换了什么"，再看到你的请求。缓存稳定，自我感知也没有丢。

## 四、权限不靠提示词，靠写入口

这是整套设计里最容易被抄错的一点。

`remember` 工具即使被某个分支用 `tool_search` 找到了，执行时仍会检查调用者是不是 standing 的 `ultimate`；不是就拒绝。也就是说，**权限是代码里的门，不是提示词里的请求**。

同类规则还有：

- 删除记忆、回退、压缩 root、进入睡眠——只有你能做，agent 不能代做；
- 保存 agent 定义——你或 agent 都可以，但下一次启动子 agent 才生效；
- 写扩展、改核心——必须走分支，即使文件放在项目自己的 `.ultimate/` 里；
- 上游更新——只 fast-forward，遇到本地未提交工作直接拒绝。

## 五、出错了会怎样

| 故障                     | 结果                                                   |
| ------------------------ | ------------------------------------------------------ |
| 一批记忆里有一条不合法   | 整批拒绝，索引与正文不会半写                           |
| 某条记忆过时             | 下一次 Dream 或记忆审查会提出更新；你也可以直接 forget |
| 扩展的 server facet 抛错 | 保留上一版本，其余扩展继续跑                           |
| 扩展的 web facet 抛错    | 该面板显示错误卡，界面其余部分正常                     |
| 新核心类型检查失败       | 旧进程继续服务，你拿到错误信息                         |
| 新核心启动失败           | 回滚到旧 generation，已批准的重启记录不会重复执行      |
| 上游有本地未提交工作     | 拒绝更新，不 stash、不 rebase                          |

注意最后一条：**"拒绝"本身就是保护**。很多自更新系统出事，不是因为没有回滚，而是因为一开始就不该执行。

## 六、常见误解

**"自进化 = 自动改代码。"**
不是。Dream 只写 journal 和提案，不改代码、不改记忆、不改设置。批准的提案变成普通分支，和人类提的需求走同一条 review + lander 流程。

**"记忆就是聊天摘要。"**
不是。记忆是**索引**：一条 slug、一行摘要、一段正文、一个来源。新分支从索引开始，需要时再读正文；完整历史仍然可查。

**"改了文件就生效。"**
取决于层。记忆立即生效，指令在下一次请求生效，扩展热重载，核心必须重启。把 L5 当 L1 用，是这类系统最常见的翻车方式。

**"模型会遵守规则。"**
设计假设它不会。所以每个危险动作都在执行点检查调用者，而不是在提示词里请求它自觉。
