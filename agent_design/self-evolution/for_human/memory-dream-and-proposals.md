# 记忆、Dream 与提案

Ultimate 的"经验"存在两个地方：**项目记忆**（短、可检索、每个分支都带着走）和 **Dream 的 journal**（长、按章节归档、需要你决策）。这篇文章解释两者怎么工作，以及为什么这样分工。

## 一、项目记忆：一份小索引，不是一本日记

记忆挂在项目的 root 会话上，只有一份。每条记忆长这样：

| 字段      | 含义                                                 |
| --------- | ---------------------------------------------------- |
| `kind`    | `decision`（决定）、`fact`（事实）、`lesson`（教训） |
| `line`    | 一行摘要，不超过 120 字符                            |
| `body`    | 正文，不超过 2000 字符                               |
| `source`  | 来源，例如 `#12/34`（会话 12 的第 34 条）            |
| `updated` | 更新时间                                             |

约束是硬的：最多 150 条，slug 必须是 `^[a-z0-9][a-z0-9-]{0,47}$`。到了上限，新经验必须合并进旧条目，而不是无限追加。

三个设计后果：

1. **记忆必须被"编辑"，不能只被"追加"。** 上限逼着 agent 做取舍。
2. **每条记忆都能追溯。** `source` 指回具体对话，不是模型凭印象编的。
3. **写入是整批的。** 一批操作先在一个副本上全部校验，通过才落盘；有一条不合法，整批拒绝，不会出现"索引说改了、正文没改"。

## 二、记忆的四个写入口

| 入口            | 谁触发                     | 做什么                                                       |
| --------------- | -------------------------- | ------------------------------------------------------------ |
| `remember` 工具 | @ultimate                  | 写一批 add/update/delete；其他 agent 调用会被拒绝            |
| 落地蒸馏        | 系统                       | 每次代码落地后，后台读落地说明和提交者摘要，自动生成记忆操作 |
| 记忆审查        | @ultimate 启动一个只读分支 | 逐条核查记忆是否仍成立，返回变更集，**不直接写**             |
| 你              | Memory 面板                | 删除记忆、压缩 root；这些动作 agent 不能代做                 |

落地蒸馏值得一提：它让"每次合并代码都沉淀一点项目知识"变成自动行为。但自动路径不追求严格——超长的摘要会被修剪，不合法的 slug 会被改成 kebab-case，宁可缩短也不整批拒绝。写入失败最多重试一次，再失败只发一条提示，绝不阻塞落地。

## 三、brief：新分支从哪开始

新分支不是从零开始，也不是把整个项目历史塞进上下文。

从有记忆的 root 分出来的分支，会先拿到一份 **brief**：

```
<project_memory root="#3">
  （按 slug 排序的记忆索引，一行一条）
  （最近 10 条落地）
  完整历史在 root 的 tally 里，可按需读取
</project_memory>
```

然后分支的模型上下文从这条 brief 开始。要点是：**brief 是索引，不是摘要**。

- 想知道某条记忆的细节，用 `memory {read}` 读正文；
- 想知道某次改动为什么发生，用 `ultimate.entries(root)` 读原始对话；
- 所以 brief 可以很小，但信息没有丢。

侧栏的 Memory 行会显示"新分支从多少 token 开始"，这个数字就是 brief 的体量——它是项目记忆成本的直接体现。

## 四、Dream：把历史变成提案

Dream 是一次**反思工作会话**。它读回项目历史、记忆、失败记录和工具使用，写一份 journal，提出若干变更建议。它自己不改代码、不改记忆、不改设置。

### 什么时候会发生

| 触发         | 条件                                                                              |
| ------------ | --------------------------------------------------------------------------------- |
| 你按 Dream   | Memory 面板或命令面板                                                             |
| 上下文快满了 | @ultimate 的上下文超过 70%                                                        |
| 你离开很久   | 上下文 50% 且空闲 8 小时（"Dream after a pause"）                                 |
| handoff 之后 | @ultimate 在上下文满前写下交接，等所有会话空闲后启动；30 分钟没有交接则无交接启动 |

### 六个 pass

Dream 会并行开六个只读的反思子 agent，每个盯一个维度：

| pass        | 它问的问题                                                           | 产出                                 |
| ----------- | -------------------------------------------------------------------- | ------------------------------------ |
| memory      | 哪些记忆过时、矛盾、重复或太模糊？哪些教训没人记？                   | 记忆操作 + 理由 + 证据               |
| failures    | 什么经常失败？watchdog、trace、重试、lander 拒绝、用户中断各占多少？ | 按原因分组的失败榜 + 修复建议        |
| tools       | 哪些工具没人用？哪些总失败？哪些该拆该合？                           | 教、删、补工具的建议                 |
| corrections | 用户反复纠正什么？agent 反复手做什么？                               | 流程 / 工具 / 指令改进               |
| codify      | 哪些记忆应该变成代码、lint、定义或技能，而不是继续靠记？             | 代码 / 规则 / 定义 / 技能 / 保留记忆 |
| project     | 这个项目里反复出现的手工步骤、环境坑、重复要求是什么？               | 在项目自己的 `.ultimate/` 里构建什么 |

每个 pass 都必须先读 @ultimate 的 handoff，再用工具去验证 handoff，不能盲信。每条主张要引用具体会话、trace 错误、commit 或代码位置。

### journal 与提案

journal 只写一次，重复调用返回已归档的那份。它包含：

- `learned`：恰好三行，Ultimate 自己的口吻；
- `text`：Markdown，每个 pass 一节；
- `proposals`：每条有 id、来源 pass、标题、规模、风险；
- `chapter`：2–3 个单词，给这段时间起个名字。

提案有四个状态：`approved`（批准并生成分支）、`rejected`（拒绝）、`applied`（记忆已改）、`landed`（分支已落地，带 sha）。分支落地后，系统会自动把对应提案标成 `landed`。

## 五、"睡着"是什么

当 journal 已归档、所有提案都有结论、没有其他会话在工作，而且各项检查通过，你可以让 Ultimate **睡着**：它做一次章节切换（备份、journaled restart、进入新 generation），就像换了一个工作日。

agent 只能询问，不能自己按这个按钮。这是整套机制里风险最高的动作，所以保留了三件套：journal、审批、回滚。

## 六、为什么这样设计

**如果记忆是摘要**：摘要会丢信息，而且每读一次就要重新生成一次，成本高且不稳定。索引 + 按需读正文，既便宜又可追溯。

**如果 Dream 自动改代码**：反思的质量无法保证，错误会被放大，而且没有人能说清"这次改动是谁批准的"。所以 Dream 的产物是提案，不是提交。

**如果记忆审查能写**：就是自己审自己。审查分支只读，变更集交回 @ultimate，再由你决定是否应用。

## 七、你能做什么

- 在对话里直接说"记住：……"，@ultimate 会写成一条记忆；
- 打开 Memory 面板，看索引、读正文、删除过时条目、压缩 root；
- 按 Dream，读 journal，逐条批准或拒绝提案；
- 让一个分支做记忆审查，看它列出的过时项；
- 在 hands-off goal 模式下，让 @ultimate 代你决策——但每条都会记录理由。
