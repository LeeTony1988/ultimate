# 为什么是两个 app

## 一、问题不是"看不到日志"，而是"看不到结构"

Agent 干活时，日志从来不缺：会话、工具调用、token 数、错误堆栈都在。缺的是把它们组织成能回答问题的结构。

一个具体的下午：

> 一个分支跑了四十分钟还没结束。你想知道：它在等什么？是某个 worker 卡住了，还是一个检查一直失败？上次同样的任务只用了十分钟，这次为什么慢？

聊天记录能告诉你"最后一句说了什么"，但回答不了：

- 哪些任务在并行，哪些在等依赖？
- 关键路径是哪一条？
- 哪个 agent 在等另一个 agent 的答案？
- 这次和上次相比，多了哪几步？

这两类问题，恰好对应两种不同的结构。

## 二、两类问题，两个投影

| 问题                                         | 需要的结构                    | 应用          |
| -------------------------------------------- | ----------------------------- | ------------- |
| 这次 run 的计划执行到哪了？为什么慢/失败？   | 任务图 + 时间线 + 详情 + 回放 | **TaskScope** |
| 谁在什么时候做了什么？工作是怎么被交出去的？ | 层级 + 时间 + 消息边          | **AgentLoom** |

同一个 run，在 TaskScope 里是一张任务 DAG；在 AgentLoom 里是一组泳道。它们看的是同一批事件，但回答的问题不同：

- TaskScope 关心**任务之间的依赖与状态**；
- AgentLoom 关心**agent 之间的委派与消息**。

把两者塞进一个界面，结果通常是两套导航、两套筛选、两套术语，谁都不好用。

## 三、共享内核

两个 app 共享三层：

```
        ┌──────────── TaskScope 视图 ────────────┐   ┌──────────── AgentLoom 视图 ────────────┐
        │  DAG · 时间线 · Inspector · 回放 · 对比  │   │  Lanes · Spawn Tree · Messages · Cost  │
        └────────────────────┬───────────────────┘   └────────────────────┬───────────────────┘
                             └──────────────┬─────────────────────────────┘
                                            ▼
                              @orchestra/ui（卡片、状态色、时间轴基础组件）
                                            ▼
                              @orchestra/core（事件模型、状态映射、算法）
                                            ▼
                              adapters（Ultimate / JSONL / OTLP）
                                            ▼
                              本地 SQLite（append-only 事件 + 投影）
```

共享带来的好处不只是省代码：

- **同一套状态词。** `running`、`blocked`、`failed` 在两个 app 里含义一致，不会一个说"等待"一个说"阻塞"。
- **同一套数字。** token、耗时、关键路径用同一份计算逻辑，不会出现两个 app 报不同的成本。
- **同一套适配器。** 支持一个新数据源，两个 app 同时受益。

## 四、为什么默认只读

观察工具的第一原则是**不要改变被观察的东西**。

只读带来三个具体好处：

1. **安全。** 一个能 stop/steer 的观察工具，一旦 bug 就是生产事故。
2. **可复现。** 同一份数据，今天看和明天看应该一致；只读保证了这一点。
3. **可离线。** 没有控制通道，就能用导出的 JSONL 完整回放一次运行。

控制能力（steer、stop）规划在 v2：需要显式授权、二次确认和审计日志，而且不会成为默认能力。

## 五、数据从哪来

两个 app 都吃同一类输入：

- **Ultimate 实时源**：任务图、事件流、trace、子 agent 事件；
- **JSONL 回放源**：导出的运行记录，用于离线分析和测试；
- **OTLP 导入**：标准 trace 作为补充，但只作为适配器，不把 OTel 属性直接泄漏到界面模型。

内部统一成 `orchestra.event.v1`（AgentLoom 另加 `orchestra.agent.event.v1`）。这条边界很重要：**标准协议负责进来，内部模型负责表达**。否则界面会被某个外部标准的字段命名绑死。

## 六、技术选型的取舍

两份 spec 都默认 **Electron 45 + React 19 + TypeScript + SQLite**，原因是"让一个 AI agent 在 3–4 周内复刻出来"：单一语言、Node 生态、可以直接复用 Ultimate 的 TypeScript 类型。

如果第一约束变成安装包体积或内存，就换 **Tauri 2.12.5**：Rust 侧只做 SQLite、SSE、文件监听，前端不变，替换点集中在一处。

选型不是信仰问题，是权重问题。调研备忘录以"产品分发"为第一约束，spec 以"复刻速度"为第一约束，所以两边给出的结论不同——这不是事实冲突。

## 七、它们刻意不做什么

- 不是聊天记录浏览器；
- 不是工作流编辑器（不能在这里改 DAG 或重跑节点）；
- 不是 Git 客户端（不画分支图、不做三方合并）；
- 不做多人协作与权限管理；
- 不默认存储 prompt / response 正文。
