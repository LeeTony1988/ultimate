# TaskScope：把一次任务编排看成一张图

## 一、它要回答的四个问题

TaskScope 的存在理由只有一个：让人在一个窗口里回答四个问题。

1. **现在什么在跑、什么卡住、什么失败？**
2. **关键路径是哪条？瓶颈在哪个任务？**
3. **这次运行为什么变成这样？**
4. **和上次相比，哪里变好了、哪里变差了？**

这四个问题决定了界面的骨架。如果只做一张漂亮的 DAG，第一个问题勉强能答，后三个都答不了。

## 二、四个联动视图

```
┌─────────────────────────────────────────────────────────────┐
│ 概览条：running / blocked / failed / 总耗时 / 数据新鲜度      │
├──────────────────────────────┬──────────────────────────────┤
│                              │                              │
│         DAG 视图              │        Inspector              │
│   （缩放 / 平移 / 折叠 /       │  （状态、耗时、错误、日志、     │
│     关键路径高亮）             │    产物、关联会话）            │
│                              │                              │
├──────────────────────────────┴──────────────────────────────┤
│ 时间线：每个任务的起止、等待、重试，可缩放、可与 DAG 对齐      │
└─────────────────────────────────────────────────────────────┘
```

- **DAG** 回答"谁依赖谁"。分层布局由 ELK 在 Worker 里算，不阻塞主线程。
- **时间线** 回答"时间花在哪"。同一个任务在图上是一个节点，在时间线上是一段区间；两者选中状态联动。
- **Inspector** 回答"这个任务为什么这样"。只有选中项有数据时才显示对应区块，没有数据就不渲染。
- **回放** 回答"当时发生了什么"。按事件顺序前进/后退，DAG 和时间线跟着重算。

回放和对比是同一套能力的两个方向：回放是沿时间轴走一遍，对比是把两次 run 的同一批任务并排看，标出新增、删除、变慢、变贵。

## 三、走一遍

假设你刚让一个分支跑完一次重构。

1. 打开应用，概览条显示：`42 个任务，3 个失败，关键路径 18 分 20 秒`。
2. 点"失败"，DAG 里三个红点高亮。其中一个不在关键路径上，说明它不是这次变慢的原因。
3. 选中关键路径上最长的那个任务，Inspector 显示它在等一个外部检查，重试了两次。
4. 切到时间线，看到第一次重试和第二次之间隔了 6 分钟——那是检查超时，不是模型慢。
5. 打开回放，拖到 12:40，看到检查第一次失败时的错误输出。
6. 和上一次 run 对比：同一个任务上次 3 分钟，这次 18 分钟，差异集中在检查阶段。

六个动作，回答的就是那四个问题。

## 四、数据是怎么进来的

```
Ultimate 任务图 / 事件流 ─┐
JSONL 导出文件 ──────────┼─► 适配器 ─► orchestra.event.v1 ─► SQLite（append-only）
OTLP trace ──────────────┘                                   │
                                                             ▼
                                              投影：任务图、时间线、关键路径
```

三条原则：

1. **事件是真相。** 图和时间线都是事件的投影，随时可以从头重算。
2. **适配器负责翻译，界面不认外部协议。** OTel 的 `gen_ai.*` 只活在适配器里。
3. **保留关联键。** `traceId` / `spanId` / `parentSpanId` 必须留，否则任务图和调用树对不上。

## 五、为什么单靠 DAG 不够

DAG 能告诉你"任务 B 依赖 A"，但回答不了：

- **为什么慢？** 图上没有时间维度，看不出一段任务是算得久还是在等。
- **为什么失败？** 失败可能来自重试、超时、外部检查，节点本身只有一个红色。
- **和上次比呢？** 两次 run 的图可能一样，但耗时结构完全不同。

所以时间线不是 DAG 的附属品，而是同等重要的第二投影。两者的选中状态必须联动，否则用户会在两个视图之间反复找同一个任务。

## 六、规模与性能

目标规模是 **1 万个任务、10 万条事件**不崩。

做法不是"优化渲染"，而是在架构上避开最贵的操作：

- 布局在 Web Worker 里算，主线程只负责画；
- 大图默认折叠，展开才计算子图；
- 时间线用 Canvas 画，不为每个任务建 DOM 节点；
- 增量布局：新事件只影响局部，不重排全图；
- 查询走 SQLite 索引，不把全量事件读进内存。

性能预算写在 spec §8，包含首屏、布局、回放拖动、对比这几条路径的上限。

## 七、它刻意不做什么

- 不编辑任务图，不重跑节点，不改变被观察的系统；
- 不做通用工作流调度器；
- 不做聊天记录浏览器（想看对话去对应会话）；
- 不把 OTel 属性直接暴露成界面字段；
- 不做多人协作。
