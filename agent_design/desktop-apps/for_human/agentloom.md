# AgentLoom：谁在什么时候做了什么

## 一、它看的是什么

AgentLoom 面对的是一群互相委派的 agent。它要回答的不是"任务图长什么样"，而是：

- 现在有哪些 agent 在跑，谁在等谁？
- 谁 spawn 了谁，是从哪一个工具调用开始的？
- 消息和报告怎么在 agent 之间流动？
- 哪个 agent 最贵、最慢、失败最多？
- 一次失败的链路上，第一个出错的是谁？

聊天记录回答不了这些问题，因为它是一条线；多 agent 运行是一棵树加一张网。

## 二、为什么是"时间 × 层级"

任务编排的天然结构是 DAG：依赖关系本身就是图。

Agent 编排的天然结构不一样。父子关系是一棵树，但真正发生的事是"每个 agent 在某个时间段里做了什么"。所以主视图不是图，而是**泳道**：

```
coordinator  ████████████████████████████████████████
  ├ worker-1     ██████████        ██████
  ├ worker-2        ██████████████
  └ reviewer            ████   ████
                └── 时间 ──────────────────────────►
```

每一行是一个 agent，按生成树缩进；一个色块是一段 run；色块上的刻线是工具调用或模型调用。

为什么泳道比 DAG 好：

- **等待看得见。** 一段空白就是没在干活，是被依赖卡住，还是在等答案，一目了然。
- **并行看得见。** 同一时间有几行在动，就是几路并行。
- **层级看得见。** 缩进直接表达"谁是谁的下属"，不需要点开节点。

纯 DAG 也能画父子边，但它把时间压扁了；而"谁在何时做了什么"这个问题，时间不能压扁。

## 三、四张视图

| 视图           | 回答什么               | 关键设计                                                                    |
| -------------- | ---------------------- | --------------------------------------------------------------------------- |
| **Lanes**      | 谁在跑、谁在等、谁空闲 | agent 一行，run 一块，调用一刻线；悬停高亮祖先/后代链                       |
| **Spawn Tree** | 谁创建了谁、为什么创建 | 边必须能追到父的具体工具调用；标出 branch / standing / subagent 与 worktree |
| **Messages**   | 工作和答案怎么流动     | 只画方向、类型（消息/报告/回复/steer）和时间，不显示正文                    |
| **Replay**     | 当时到底发生了什么     | 按时间前进/后退，重建那一刻的泳道与消息                                     |

辅助视图与面板：

- **Inspector**：选中 agent 后显示状态、模型、token、工具、workspace 和关联的 plan task；只显示有数据源的字段；
- **Cost**：按 agent 聚合 input / output / cache，回答"谁烧的钱"；
- **Compare**：两次 run 并排，标出新增的 agent、变慢的环节、变贵的模型。

## 四、走一遍

一个分支跑了半小时，最后失败。

1. 打开 Lanes，看到 coordinator 一直亮着，worker-2 有一段很长的空白。
2. 悬停 worker-2，祖先/后代链高亮：它是 coordinator 的子，下面没有别人。
3. 切到 Messages，发现 coordinator 在 12:10 给它发了一条 steer，之后没有任何回复。
4. 打开 Spawn Tree，确认 worker-2 是在 11:55 由 `subagent start` 创建的，带独立 worktree。
5. 拖回放到 12:10，看到消息发出时 worker-2 正在跑一个很长的工具调用。
6. 看 Cost：worker-2 的输入 token 是别人的三倍——它在反复重读同一批文件。

六步之后，"为什么失败"不再是一个猜测。

## 五、三个关键细节

### 1. spawn 边必须能追到工具调用

只画"coordinator → worker"没有用。用户会问：为什么会有这个 agent？它是在哪一步被创建出来的？

所以每条 spawn 边都要带父的调用 id。数据不支持时（例如事件里没有 callId），适配器要做推断，并在界面上标明这是推断结果，而不是假装确定。

### 2. 消息边不显示正文

消息边表达的是**结构**：谁发给谁、是 steer 还是 follow-up、是否回复、什么时候。正文属于会话，不属于可视化。

这样做有三个好处：界面清爽、隐私风险低、数据量小。想看内容，点进会话。

### 3. 成本必须按 agent 聚合，并区分缓存

一次运行的总账单回答不了"谁烧的"。必须能下钻到 agent、模型、输入/输出/缓存命中。否则优化成本只能靠猜。

## 六、规模与性能

目标规模是 **200 个 agent、10 万次调用**。

- 泳道用 Canvas，不为每个调用建 DOM 节点；
- 时间范围分档（30 分钟 / 2 小时 / 24 小时 / 全部），只加载可见区间；
- 生成树和消息边按需计算，不随每次 tick 全量重排；
- 实时流断线后按快照对账，不重复插入。

## 七、只读与隐私

- v1 默认只读，不写 Ultimate 的数据库；
- 控制能力（steer / stop）属于 v2，需要显式授权、二次确认、审计日志；
- **默认不存储 prompt / response 正文**，只存结构化元数据；
- 数据落在本地 SQLite，不出机器。

## 八、它刻意不做什么

- 不做 agent 搭建器（不能在界面里定义新 agent 或改 prompt）；
- 不做通用 LLM 观测平台（没有 eval、评分、数据集管理）；
- 不展示完整对话正文；
- 不替代聊天界面，只做它的空间化补充。
