The live durable task graph in the right panel's Tasks tab, grouped by what the work means rather than who owns it (`kinds.ts`):

- **Running:** each conversation with a turn, as a tree by owner (turn → tool calls → the conversations a task owns, such as subagents). Top-level conversations show their feature tag; one linked to a plan task shows the plan's `TaskChip`. Click a conversation to show it.
- **Messages:** `board.delivery` tasks in plain words: "Delivering to", "Waiting on" (a reply-enabled message placed and not yet answered), "Delivered to", "Delivering the reply to", with the sender and the message's opening words; subagent reports and notify-when-done watches too.
- **Landing**, **Scheduled** (automations and watchdog retries, with when they wake).
- **Background**, folded to a count: summaries, routing, notes and other chores. A blocked chore or one past ten minutes stays out of the fold.

No row is named after the root conversation: work it owns (deliveries, automations) is the project's. Each row's hover shows the raw kind, id, phase and owner. Durations come from the task record's durable `startedAt` (warning colour after ten minutes, so a stuck task stands out). Names come from the `describe {ids}` action, which reads each task's input once (a message's ids and text, an automation's name, a tool's name, a lander's submission); an unknown kind shows its raw name in Background.

The composer's status line shows the shown conversation's open messages (`messages/open.tsx`): how many answers it waits for, owes and is still delivering; a click lists them, and each row opens its conversation.

A task Pi Durable cannot run shows why (missing or too-old definition, failed migration); these clear when the registry changes. A task cut off by crashes `restartLimit` times in a row is not shown here: Pi ends it, and its run, tool call or compaction shows the failure.

Data comes from `useTasks()` (the server's `tasks` event), `useConversations()`, the conversations overview and the messages log; start times and facts come from the `started {ids}` and `describe {ids}` actions, each asked once per task since they never change.

The **Task DAG** surface (order 65, also opened from the Tasks tab's `DAG ↗` link and the `Show the task DAG` command) is durable run history. A displayed run is one input submission through its answer, including every model generation and tool round in between and the steers that share that answer. It is reconstructed from committed submissions, entries and task records: shared answers and task ownership are proof; successive generation rounds and child-agent anchors are ordered evidence and are labelled **inferred** in the frame header. A user turn whose reset/turn-limit boundary is indistinguishable from an unanswered steer is kept as a separate run with an uncertainty note, never silently merged. The left rail lists conversations (checkboxes; the current conversation is selected on first open) and their runs, newest first. Each checked conversation gets its own titled frame; proven child-agent conversations open as nested frames. Frames are ordered by their earliest task.

**Structure** (the default tab) draws the existing layered columns inside each frame: solid owner edges, dashed `on` waits that are still present in live records, dimmed finished tasks (no 30-second drop), warning-coloured failures, a `+N` chip for a finished subtree (folded by default, click to expand), and an optional dependency-chain highlight. **Timeline** is a separate tab: x is time since the run started, one lane per agent and one for its tools with a row per task, a bar per task, current waiting edges and a hover card. Terminal task records do not retain earlier waiting states, so past wait edges cannot be reconstructed here. A recorded usage total can omit retry attempts or nested calls whose result entries are gone; unknown is left blank.

**Constellation** is the third tab: one dot cluster per checked conversation, using every visible `RunSummary` for the conversation: each turn is an independent line from the conversation root, completed turns stay fixed, and only the live turn merges `mergeRunLive` over `useTasks()`. Nodes are pure circles, never cards or icons: task type sets the radius, status sets brightness/opacity/ring, and a failed step keeps the task's hue with a broken ring. `pi.generation` and `pi.compaction` are turn boundaries and never visible dots; tool dots read from `TaskFacts.tool` plus the useful part of the task detail (for example `powershell · npm test`, `read · extensions/tasks/graph.tsx`). A cluster's dots and edges share one hue, spaced at least 60° apart across up to six clusters; edges never leave their cluster. Each cluster has a faint irregular halo made of three offset blurred ellipses, never a circular boundary or progress arc. Hovering a dot lights its whole cluster and dims the rest; a click focuses a node, a cluster title focuses the cluster, and Esc steps back out. The canvas pans, zooms at the cursor (0.32–2.6), fits on double click or `0`, and a minimap moves the camera. Dragging empty space inside a cluster moves that cluster; Reset clears the manual offsets and Fit only moves the camera. `tasks.dag.clusterOverlap` (0–0.6, default 0.3), `visualClustering` (0–1), `crossRepulsion` (0–1), `labels` and `pulse` live in the header/settings popover; the server rejects values outside their ranges. Each turn keeps its head and tail when it exceeds seven visible steps, reporting the omitted middle; `prefers-reduced-motion` disables pulse and edge flow.

Settings live in the project's `.ultimate/settings.json` as `tasks.historyDays` (default 3) and `tasks.costDetail` (`run`, or `tool` for per-call token/cost detail), editable from the gear in the surface header after local project setup is trusted. They filter what is visible; history rows are never deleted. Server actions are read-only (`conversations`, `history`, `run`) except the settings write. `history` pages 20 runs at a time; `run` caps a run's tasks at 5000 and flags truncation. The surface merges live `useTasks()` nodes over the stored records by id, so a run in progress keeps updating without a refresh. Token and cost figures are labelled **recorded**: retry attempts and nested calls whose results are no longer retained may not be included.
