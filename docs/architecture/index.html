How Ultimate fits together

Five pictures, one question each. Ultimate is a web UI and a server that runs coding agents on Pi Durable; almost everything Ultimate adds lives in extensions that reload while it runs.

01 · THE BIG PICTURE

What runs where?

The browser talks to one server process. Inside it, Pi Durable runs the agents and Ultimate's extension host runs everything else; a tiny supervisor keeps it alive and swaps it on restart.

How a change goes live

  • web/ · web.tsx hot reload, instant
  • server.ts reinstalled on save
  • server/ · shared/ restart tool: a new child type-checks beside the old
  • bin/ only a human restart

In the browser

One page; facets hot-swap in place. A broken facet shows an error card, the rest keeps running.

Around the server

The supervisor owns port 4747 and the lock. Pi Durable commits first, then shows. Git is reached through bash, edit and workspaces; model logins live in ~/.pi/agent.

02 · WHERE PI DURABLE SITS

Where does Pi Durable end and Ultimate begin?

Pi Durable stores every conversation and runs every turn as a checkpointed task. Ultimate is two layers on top: an extension host, and the features that turn conversations into a project.

After a crash or restart

Open storage, then resume(): every run continues from its last checkpoint. Tools marked replay: 'safe' run again; any other interrupted tool tells the model "interrupted".

Ultimate's patches to Pi Durable

The beforeInput placement hook and Harness.hold().

Underneath

Storage is state.sqlite (SQLite); models come from pi-ai; the coding tools come from Pi.

03 · EXTENSIONS AND THEIR INTERFACES

How do extensions connect?

An extension is a folder with a contract for the server (api.ts) and one for the browser (refs.ts). Four channels connect extensions, and dependencies always point down.

Calling up: an extension point

The lower layer owns the contract and wants it; the higher one implements it. workspaces (4) does want(Branches), messages (7) does implement(Branches), through workspaces.branches: the lander asks who started a branch and whether work is still under way.

Optional extensions

They plug in the same way; the core tier never imports them.

Learning an extension

Agents read its api.ts and refs.ts.

04 · THE EVENT BUS, THROUGH ONE LANDING

What happens when work lands?

The lander writes the change and its event in one commit, so the event exists exactly when the change does. Every reactor then picks it up with its own cursor.

What the cursor buys

  • Writes through tx happen exactly once, across crashes, reloads and failures.
  • Files, processes, network: at least once.
  • A throw rolls back handler and cursor; it retries.
  • { from: 'now' }: a new reactor skips the past.

Seeing it

  • emit stamps the trace context on the event, so each reactor run continues the lander's trace.
  • eventLog.reactors(): cursor, lag, last failure.
  • ultimate.traceTree(id): the whole chain, nested, with durations.

Meanwhile, through git rather than the bus: main moves → host hot-reloads the files → next input gets "Build changed" → ↻ Reloaded · <branch> #N

05 · THE AGENT FOREST

Who talks to whom?

You talk to @ultimate; it starts a branch per piece of work. Branches delegate to subagents and land through the lander, and every landing flows back into the root's memory, which the next branch starts from.

Every box is a Pi Durable conversation

The roles are Ultimate's. Branches run one per piece of work, in parallel, each in its own worktree.

Three ways to reach another conversation

  • message / start: wakes the recipient
  • note: read at its next input, wakes nothing
  • notify: tells you when it finishes

The lander

A standing agent with its own checkout: one submission at a time; checks, then main.
